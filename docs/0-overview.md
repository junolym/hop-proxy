# 0 - 项目总览与设计哲学

## 项目定位

HopProxy 是一个**自托管（self-hosted）的内网穿透与智能反向代理系统**。它解决的核心问题是：

> **如何让运行在私有网络中的 HTTP/WebSocket 服务，通过公网子域名被外部用户访问，同时为内部网络用户提供零延迟的本地直连能力？**

### 与同类工具的对比

| 维度 | frp / ngrok 类穿透工具 | 传统反向代理 (Nginx/Traefik) | **HopProxy** |
|------|------------------------|------------------------------|--------------|
| 内网暴露 | 支持 | 不支持 | **支持**（隧道模式） |
| 公网访问 | 支持 | 支持 | **支持** |
| 内网本地访问 | 不支持（需绕公网） | 支持（需手动配置每条规则） | **支持**（自动路由，透明回退） |
| 跨机器服务互访 | 需各自暴露再经公网 | 需复杂配置 | **支持**（Peer 直连） |
| 统一域名管理 | 否 | 是 | **是**（公私网同一子域名） |
| SSO 单点登录 | 无 | 需外接 | **内置** |

## 设计哲学

### 1. 公私网同构 (Isomorphic Access)

这是 HopProxy 最根本的设计理念。

传统方案中，内网用户和公网用户访问同一个内网服务需要使用不同的地址和路径——内网用 IP:Port 或内部 DNS，公网走穿透隧道。这导致：

- 配置维护成本翻倍（内外两套配置）
- 应用代码中硬编码地址或依赖环境变量切换
- 调试困难（"在内网正常但公网不行"类问题难以复现）

HopProxy 的解法：**所有用户使用完全相同的子域名 URL 访问服务**。系统自动根据请求来源选择最优路径：

```
https://myapp.proxy.example.com/api/data
         │
         ├─ 公网用户 → Nginx → Server → Tunnel → Client → 目标
         └─ 内网用户 → DNS → LocalProxy → 本地反代 → 目标
                        （未命中则透明回退到 Server）
```

对应用而言，无论部署在哪个环境、用户从哪里来，URL 永远不变。

### 2. 三层渐进式路径选择 (Layered Path Selection)

系统不强制指定某一条路径，而是根据网络拓扑和应用配置**自动降级/升级**：

```
第一层：本地直连 (Local Direct)
    ↓ 命中失败或不可达
第二层：Peer 直连 (Peer Direct)
    ↓ Peer 不可用
第三层：服务端中转 (Server Relay)
```

每一层都是完整的代理实现（SSO 认证、流式传输、Header 处理等），确保功能一致性。上层仅在下层不可用时才激活，用户无感知。

**设计意图**：优先利用低延迟的本地资源，同时保证在任意网络拓扑下服务可达。

### 3. 服务端极简部署 (Minimal Server Footprint)

服务端设计为**单个二进制 + 单个端口**的形态：

- **单端口**：管理 API、前端静态文件、WebSocket 隧道端点、代理请求处理，全部在一个 HTTP 端口上通过 `Host` 头区分。
- **单二进制**：前端 Vue SPA 通过 Go `//go:embed` 编译嵌入，无需额外部署静态文件服务器。
- **纯 SQLite**：`modernc.org/sqlite` 纯 Go 实现，无 CGO 依赖，数据库就是单个文件。

这意味着部署新实例只需：
1. 上传一个二进制文件
2. 配置 Nginx 反代 + SSL 证书
3. 启动进程

无需安装运行时依赖、无需数据库服务、无需额外存储卷。

### 4. 客户端被动执行 (Client as Execution Layer)

客户端的设计哲学是**「只执行，不决策」**：

- 客户端不知道有哪些应用、哪些子域名
- 应用配置全部由服务端管理，客户端通过隧道协议接收指令
- 客户端的唯一决策是：收到请求后向哪个地址发起 HTTP 调用

这种设计的直接好处：
- **迭代解耦**：服务端频繁添加功能（SSO、负载均衡、Peer 等），客户端基本不变
- **安全性**：客户端不持有业务数据，泄露风险极低
- **可替换性**：同一协议下可以有不同的客户端实现（Go 版、未来可能有其他语言版）

### 5. 安全纵深防御 (Defense in Depth)

安全不是单一措施，而是多层独立防护的叠加：

```
┌──────────────────────────────────────────────┐
│ 第 1 层：传输安全                               │
│   TLS (Nginx SSL 终结) + httpOnly Cookie      │
├──────────────────────────────────────────────┤
│ 第 2 层：身份认证                               │
│   SSO Cookie / Access Token 双层验证           │
│   暴力破解限速 (5次/5分钟)                     │
│   CSRF Token (双提交 Cookie 模式)              │
├──────────────────────────────────────────────┤
│ 第 3 层：Peer 通信安全                          │
│   HMAC-SHA256 签名 + 时间戳防重放               │
│   密钥启动轮换 (每次客户端重启生成新密钥)        │
│   认证头隔离 (到达目标后清除 X-Peer-* 头)       │
├──────────────────────────────────────────────┤
│ 第 4 层：审计与可追溯                           │
│   关键操作记录审计日志 (login/sso/revoke等)     │
│   SSO Session 全生命周期追踪                   │
└──────────────────────────────────────────────┘
```

每一层独立有效，任一层被突破时其他层仍提供保护。

## 解决的问题场景

### 场景 A：开发环境的公网暴露

开发者在家/办公室的内网机器上运行开发服务（如前端 dev server、调试接口），需要临时让外部用户（客户、测试、CI）访问。

传统做法：ngrok/frp 之类的工具，每次获取不同的随机域名，且免费版有诸多限制。

HopProxy 做法：分配固定子域名 `dev-myapp.proxy.example.com`，持久可用，自带 SSO 保护防止未授权访问。

### 场景 B：混合部署的服务访问

企业环境中，部分服务部署在公有云（可直接公网访问），部分服务部署在内网（无法直接访问）。希望对外统一呈现为一套服务集群。

HopProxy 做法：公网服务的目标地址设为云主机的公网 IP（甚至可以用 `__host__` 本机模式），内网服务的目标地址设为内网 IP + 关联内网客户端。对外统一通过子域名访问，调用方无需感知部署位置。

### 场景 C：内网多机器服务互通

微服务架构中，Service A 运行在机器甲，Service B 运行在机器乙，两者都在内网但不在同一台机器上。Service A 需要调用 Service B 的 HTTP 接口。

传统做法：每个服务单独配置内网地址；或者搭建一套内部 Service Mesh（重）。

HopProxy 做法：将 Service B 注册为一个应用，Service A 所在机器的客户端配置 Peer 代理指向 Service B 的客户端。A 通过 `service-b.proxy.example.com` 访问 B，走内网 Peer 直连。

### 场景 D：带权限控制的外部服务暴露

需要将某个内网 Web 工具（如 GitLab、Jenkins、Grafana）临时开放给外部合作伙伴访问，但不想暴露给所有人。

HopProxy 做法：配置该应用的 `auth_method = sso`, `allowed_users = owner`。只有被授权的用户（拥有有效 SSO Session）才能访问，其他人看到的是登录页。

## 核心术语表

| 术语 | 定义 |
|------|------|
| **Proxy Domain** | 代理域名的上级域名（如 `proxy.example.com`），所有 `*.proxy_domain` 格式的 Host 都被视为代理流量 |
| **Admin Domain** | 管理后台的域名（可与 Proxy Domain 相同或不同），用于访问管理界面和 API |
| **Subdomain** | 子域名前缀（如 `app1`），全局唯一，映射到一个应用配置 |
| **App** | 应用配置项，包含子域名、默认目标地址、认证方式等元信息 |
| **Client** | 客户端实例，以 UUID 标识，运行在内网机器上，负责与服务端建立隧道并执行代理 |
| **Tunnel** | 服务端与客户端之间的持久 WebSocket 连接，经 yamux 多路复用为多条独立流，承载代理请求与控制流（每请求一流，流首字节为 StreamType） |
| **Host Client (`__host__`)** | 特殊客户端标识，表示目标服务运行在服务端本机，无需隧道 |
| **Local Proxy** | 客户端可选启用的本地 HTTP 监听服务，处理内网用户的直接请求 |
| **Peer** | 客户端之间的直接 WebSocket 通信隧道，不经过服务端；gob 认证后升级为 yamux 会话，请求经 yamux 流收发 |
| **SSO Session** | 用户对某个应用的授权会话，以加密 Cookie 形式存储在浏览器中 |
| **Access Token** | 应用的 API 访问令牌，用于非浏览器客户端（curl、程序化调用）的程序化认证 |
